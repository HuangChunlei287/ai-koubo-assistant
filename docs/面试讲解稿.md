# 2–3 分钟面试讲解稿

> 原则：只讲真实做过的。访谈 3 人、测试 8 条已真实完成；3 名用户体验 Demo 仍是待办，不要写成已完成。

## 开场（20 秒）

> 我做的是一个「AI 口播创作助手」，面向探店、种草、知识分享类的中文短视频创作者。它不解决剪辑，而是解决开拍前最耗时的准备：从一个主题，生成可编辑的口播脚本，再拆成能直接照着拍的镜头，最后给出字幕重点词和发布文案。

## 为什么做这个（30 秒）

> 我自己观察到的现象是：很多创作者不是不会拍，而是卡在「第一句说什么」和「每个镜头拍什么」。现有工具要么只帮写文案，要么只做字幕，流程是断的。
>
> 我访谈了 3 名有短视频创作经历的人：一位做小吃街探店，一位做文创店探店，一位做散步随拍。他们最常提到的三个问题是：脚本开头难写、内容取舍耗时、拍摄时容易忘词/卡壳。
>
> 有意思的是，三个人最想要的功能不一样：一个要脚本，一个要重点词，一个要分镜。这让我确定产品不能只做一个功能，而要把这三件事串起来，让不同卡点的人从不同入口进入。

## 为什么先做脚本和分镜（20 秒）

> 因为这三件事正好对应三种卡点：U1 卡在脚本台词，U2 卡在录制时啰嗦、需要重点词，U3 卡在一镜到底、需要分镜。剪辑、配音、数字人这些是成片环节，工具已经很多；但「主题到可拍清单」这一段反而没人做好。MVP 刻意不做视频生成，是为了先验证脚本、重点词和分镜对创作者是否真的有价值。

## 怎么实现的（40 秒）

> 前端是 Next.js + TypeScript，后端用 API Route 调大模型。整个流程拆成三个接口：
>
> 1. 主题 → 口播脚本：输入主题、平台、受众、时长、风格，输出钩子、正文、行动引导；
> 2. 脚本 → 分镜：把脚本按语义拆成镜头，输出景别、机位、构图、氛围、台词、字幕、重点词；
> 3. 脚本 → 发布文案：输出标题候选、封面短句和平台描述。
>
> 模型层做了供应商适配，目前主要用 DeepSeek，因为它国内直连、成本低；代码里也保留了 Gemini、OpenAI、Anthropic 的适配。API Key 通过服务端加密后存 HttpOnly cookie，不进前端代码。

## 遇到的最具体问题（40 秒）

> 最具体的是模型输出不稳定。原项目是给 Gemini 设计的，Gemini 有强 schema，能保证字段齐全；换成 DeepSeek 后，它虽然返回合法 JSON，但会把 `dialogue` 写成字符串、把镜头序号全写成 0、漏掉构图和氛围。
>
> 我的处理是两层：第一，改提示词，把字段格式和「序号从 1 开始」写死；第二，在服务端加确定性规范化，自动补字段、重排序号、把字符串台词转成数组、从台词重算字幕。这样模型偶尔不听话，页面也不会缺台词。
>
> 还有一个前端问题：React 事件里的 `currentTarget` 在状态更新函数执行时已经被清空，导致输入框报 `Cannot read properties of null`。改成先在事件里取值再更新就好了。

## 怎么判断质量 / 测试（30 秒）

> 我设计了 12 条测试用例，实际执行了 8 条，覆盖正常输入、空主题、超长输入、特殊字符、不同时长、平台/画幅、接口异常、重复生成与复制。
>
> 测试 5（分镜总时长）和测试 6（平台画幅）第一次失败，修复后复测通过；开发中还修复了 DeepSeek 把 dialogue 返回成字符串的问题。测试记录在 `docs/测试用例.md`。

## 用户反馈与迭代（30 秒）

> 需求访谈和测试已经完成，但 3 名目标用户体验 Demo 的可用性测试还没做，所以这里没有可汇报的反馈数据。下一步会邀请 3 名创作者实际走一遍流程，记录卡点，再改一轮；不会把计划写成已完成的结果。

## 限制与下一步（20 秒）

> 目前的限制是：本地单用户、没有账号体系；不做视频渲染；分镜还不能逐字段编辑，只能改脚本后重新生成；发布文案没有接平台发布 API。
>
> 如果再做一周，我会优先做两件事：第一，让分镜支持逐字段编辑；第二，把入口拆成「没脚本 / 有脚本 / 只要重点词」三种模式，适配访谈里发现的三种卡点。

## 可能被追问的问题

**Q：为什么不用现成的 AI 视频工具？**
> 因为我的用户是真人口播创作者，他们需要的是拍摄清单，不是 AI 生成的成片。AI 视频工具解决不了「我今天要拍什么、怎么拍」的问题。

**Q：为什么选 DeepSeek？**
> 国内直连、按量计费、OpenAI 兼容，接入成本低。缺点是 JSON 结构不如 Gemini 稳定，所以我加了服务端规范化层。

**Q：你怎么保证生成内容不瞎编？**
> 提示词明确要求不编造脚本里没有的价格、地址、销量、年限；脚本和分镜都保持台词逐字一致；发布文案只基于脚本内容。但模型仍可能出错，所以结果必须可编辑，测试里也有对应用例。

**Q：只访谈 3 个人，样本是不是太小？**
> 是便利样本，不能代表所有创作者。但 3 个人已经出现了三种不同的卡点，说明需求不是单一的；下一步会扩大样本，并用 3 名用户的体验测试验证哪条路径最常用。

**Q：这个项目你一个人做了多久？**
> 【待填：真实时间，例如 5 天集中开发 + 2 天访谈测试】。

**Q：如果用户说不好用，你怎么办？**
> 先看是哪一步卡住：是脚本不能用、分镜看不懂，还是流程太长。然后用访谈/可用性测试定位，不先加功能。
